# ARKHAM — فروشگاه عسل

این مخزن یک پیاده‌سازی قابل اجرای فروشگاه است، نه صرفاً صفحه نمایشی. **هنوز مجوز راه‌اندازی فروش واقعی نیست.** وضعیت دقیق، آزمون‌ها و موارد ناتمام در `docs/STATUS.fa.md` آمده است. در V3، محتوای نمایشی فقط با فرمان اختیاری seed_demo و در محیط دمو وارد می‌شود؛ هیچ نظر، مشتری یا سفارش پرداخت‌شده ساختگی اضافه نمی‌شود. داده‌های تست خودکار همچنان در دیتابیس موقت ساخته و حذف می‌شوند.

## معماری

- فرانت‌اند: React 19 + TypeScript + Vite، فارسی/RTL، فونت محلی Vazirmatn با مجوز OFL.
- صحنه سه‌بعدی: Three.js + React Three Fiber، مدل procedural شیشه، کندو، زنبور و ذرات؛ بارگذاری مستقل و fallback تصویری محلی. این تصویرسازی عکس محصول واقعی نیست؛ نشان رسمی ارسال‌شده مالک روی برچسب به کار رفته است.
- سرور: Django 5.2 LTS + DRF؛ لایه‌های models / serializers / API / services / payments / web. دامنه‌ها فعلاً در اپ `store` هستند؛ تفکیک به چند Django app هنوز انجام نشده است.
- دیتابیس: PostgreSQL 16؛ قیمت‌ها Decimal بدون اعشار، **واحد داخلی تومان**. تبدیل به ریال فقط در آداپتر درگاه و داده ساختاریافته SEO.
- احراز هویت: Django Session / CSRF، هم‌مبدأ. نیازی به CORS باز یا ذخیره توکن در localStorage نیست.
- Production: Nginx غیرروت + Gunicorn غیرروت + PostgreSQL + Redis برای rate limit مشترک؛ TLS در reverse proxy میزبان. صف Celery اضافه نشده؛ اعلان‌ها درون حساب کاربری ثبت می‌شوند.
- SEO: پوسته HTML سمت Django، metadata و محتوای قابل خواندن بدون JS برای محصول/مقاله/صفحه محتوایی؛ React بخش تعاملی است. این معماری Next.js SSR کامل نیست.

## اجرای محلی (Linux / Python 3.13 / Node 24 / PostgreSQL 16)

ابتدا PostgreSQL را با دیتابیس UTF-8 و یک کاربر محلی آماده کنید. برای اجرای تست، کاربر محلی باید مجوز ساخت دیتابیس داشته باشد؛ **کاربر Production نباید به این مجوز نیاز داشته باشد**.

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r backend/requirements.txt
cd frontend
npm ci
npm run build
cd ..
export DEBUG=1
export SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(60))')"
export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5432
export POSTGRES_DB=arkham POSTGRES_USER=arkham
# POSTGRES_PASSWORD را در محیط امن تنظیم کنید؛ در فایل عمومی ننویسید.
export PAYMENT_PROVIDER=mock
export PUBLIC_ORIGIN=http://127.0.0.1:8000
cd backend
python manage.py migrate
python manage.py setup_roles
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

نشانی‌ها:
- فروشگاه: `http://127.0.0.1:8000/`
- پنل اختصاصی: `/manage` (پس از ورود با کاربر staff دارای مجوز)
- پنل داخلی: `/django-admin/`
- Swagger محلی و بدون CDN: `/api/v1/docs/`
- OpenAPI: `/api/v1/schema/?format=json`
- Health: `/api/v1/health/`

در توسعه می‌توان Vite را نیز در ترمینال دیگری با `npm run dev` اجرا کرد؛ درخواست‌های API به پورت 8000 proxy می‌شوند. Metadata سمت سرور در این حالت فقط روی پورت Django بررسی شود. SQLite فقط با انتخاب صریح `DEBUG=1 DEV_SQLITE=1` برای توسعه سبک در دسترس است و **آزمون هم‌زمانی روی آن معتبر نیست**. تست اصلی این پروژه روی PostgreSQL اجرا شده است.

## راه‌اندازی Docker

Docker Engine و افزونه Compose v2، تنظیم DNS و TLS پیش‌نیاز هستند. در این محیط Docker نصب نبود؛ Compose و imageها عملاً build/run نشده‌اند. پیش از استفاده واقعی، راهنمای `docs/DEPLOYMENT.fa.md` و چک‌لیست وضعیت را بخوانید.

```bash
cp .env.example .env
chmod 600 .env
# SECRET_KEY، POSTGRES_PASSWORD، POSTGRES_APP_PASSWORD، دامنه و سایر تنظیمات را وارد کنید.
docker compose config --quiet
docker compose up -d --build
docker compose ps
./scripts/create-admin.sh
```

Migration و collectstatic در سرویس یک‌باره `migrate` اجرا می‌شوند و backend به پایان موفق آن وابسته است. هیچ مدیر یا رمز پیش‌فرضی وجود ندارد. پورت برنامه فقط روی `127.0.0.1:8088` منتشر می‌شود؛ PostgreSQL و Redis پورت عمومی ندارند. برای مشاهده از اینترنت، reverse proxy میزبان باید TLS و هدرهای صحیح را برقرار کند.

## اولین محتوای واقعی

1. با مدیر ساخته‌شده وارد `/manage` شوید.
2. یک دسته‌بندی فعال بسازید و شناسه‌اش را بردارید.
3. محصول را با آن شناسه و نامک انگلیسی یکتا بسازید. محصول بدون `active` عمومی نمی‌شود.
4. یک گونه بسازید: شناسه محصول، SKU یکتا، وزن، قیمت تومان. موجودی اولیه صفر است؛ از «تغییر موجودی» با دلیل مستند استفاده کنید.
5. عکس واقعی را در بخش تصاویر به شناسه محصول وصل کنید. JPEG/PNG/WebP تا ۵MB و ۲۰ میلیون پیکسل؛ سرور آن را بازکدگذاری می‌کند. SVG و فایل اجرایی مجاز نیستند.
6. روش ارسال، هزینه و استان‌ها را تنظیم کنید. `[]` یعنی همه استان‌ها؛ آرایه نام استان‌ها باید با آدرس مشتری منطبق باشد.
7. محتوای رسمی و سیاست‌ها را پیش از فروش منتشر کنید.
8. فقط پس از تست sandbox/درگاه و بررسی چک‌لیست، پرداخت واقعی را فعال کنید.

### کلیدهای محتوا

در `/manage?tab=content` این کلیدهای یکتا را با `published=true` ثبت کنید:

| key | کاربرد |
|---|---|
| `hero` | عنوان و توضیح Hero |
| `story` | داستان برند و صفحه درباره ما |
| `benefits` | مزیت‌های واقعی فروشگاه |
| `contact` | اطلاعات تماس رسمی |
| `faq` | پرسش‌های متداول |
| `shipping` | ارسال و مرجوعی |
| `terms` | شرایط استفاده |
| `privacy` | حریم خصوصی |

متن مقاله‌ها و صفحات به‌شکل متن ساده امن نمایش داده می‌شود، نه HTML اجرایی. JSON مشخصات محصول باید object باشد. تنظیمات عمومی JSON ذخیره می‌شوند، ولی همه کلیدهای دلخواه خودکار در UI نمایش داده نمی‌شوند؛ فقط موارد مصرف‌شده توسط رابط کاربرد دارند. برای لوگو، بخش «لوگو و تصاویر برند» و کلید `logo-dark` را استفاده کنید؛ پس‌زمینه Hero کلید `hero-background` دارد. تنظیمات contact می‌تواند `{"socials":[{"label":"نام شبکه","url":"https://example.com"}]}` داشته باشد. فقط لینک HTTPS نمایش داده می‌شود. مدیریت کامل CTA/فوتر هنوز همه‌جانبه نیست؛ چیزی را صرفاً به‌علت ذخیره JSON، پیاده‌شده فرض نکنید.

## چرخه خرید و امنیت مالی

- سبد مهمان در سرور با Session و سبد مشتری در دیتابیس نگهداری و هنگام ورود ادغام می‌شوند.
- ایجاد سفارش نیاز به ورود، آدرس مالک، روش ارسال فعال و UUID در `idempotency_key` دارد.
- سرور قیمت جاری، بازه تخفیف، سقف مصرف کوپن و موجودی را محاسبه می‌کند. فیلدهای قیمت ارسالی مرورگر پذیرفته نمی‌شوند.
- هنگام ثبت سفارش، موجودی **رزرو** می‌شود؛ موجودی فیزیکی فقط بعد از تأیید پرداخت به‌شکل اتمیک کم می‌شود.
- قفل ردیف PostgreSQL، محدودیت‌های دیتابیس و ترتیب ثابت قفل‌ها از فروش هم‌زمان آخرین واحد و کسر دوباره جلوگیری می‌کنند.
- سفارش شامل snapshot نام، SKU، وزن، قیمت، تخفیف و نشانی است.
- Callback مرورگر اثبات پرداخت نیست. درگاه مستقیماً verify می‌شود. مرجع پرداخت یکتا است و Callback تکراری دوباره موجودی کم نمی‌کند.
- سفارش شروع‌نشده تا ۲۰ دقیقه قابل آغاز پرداخت است. برای آزادکردن رزروهای منقضی شروع‌نشده، فرمان زیر را زمان‌بندی کنید:

```bash
docker compose exec -T backend python manage.py expire_unstarted
```

**پرداخت شروع‌شده، timeout و وضعیت نامشخص خودکار آزاد نمی‌شود** تا فروشِ موجودیِ پول‌پرداخت‌شده رخ ندهد. این رفتار محافظه‌کارانه ممکن است موجودی را نگه دارد. تطبیق تراکنش و فرآیند آزادسازی مالیِ مستند هنوز نیازمند تکمیل عملیاتی است.

```bash
docker compose exec backend python manage.py reconcile_payment ORDER_UUID
```

این فرمان فقط authority موجود را مستقیماً verify می‌کند؛ تراکنش ساختگی، بازپرداخت یا آزادسازی بدون مدرک ایجاد نمی‌کند.

### درگاه

`PAYMENT_PROVIDER=disabled` پیش‌فرض امن است و ثبت سفارش پرداختی را مسدود می‌کند. `mock` فقط در `DEBUG=1` مجاز است و تأییدش POST احراز هویت‌شده می‌خواهد. تنظیم mock در Production باعث خطای startup می‌شود.

آداپتر `zarinpal` درخواست و تأیید v4 را با TLS، amount ریالی، authority ذخیره‌شده و ref_id یکتا پیاده می‌کند. Merchant ID از محیط می‌آید. **هیچ درخواست یا پرداخت واقعی زرین‌پال در این پروژه انجام/آزمایش نشده است.** قرارداد جاری درگاه، پذیرندگی، callback و خطاهای واقعی باید پیش از فعال‌سازی بررسی شوند. در این آداپتر امضای محلی جعلی اضافه نشده؛ اثبات پرداخت از verify مستقیم درگاه است، نه `Status` مرورگر.

## نقش‌ها

`setup_roles` گروه‌های مدیر فروشگاه، مدیر محصولات، مدیر محتوا، مسئول سفارش‌ها و پشتیبانی را می‌سازد. مدیر اولیه فقط `createsuperuser` است. در پنل داخلی، `is_staff` و گروه مجاز را صریحاً به کاربران بدهید. پیش‌فرض، مشتری دسترسی مدیریتی ندارد؛ `is_staff` به‌تنهایی نیز مجوز مدل‌ها را نمی‌دهد. اجرای دوباره setup_roles مجوزهای همین گروه‌های استاندارد را به تعریف پروژه بازمی‌گرداند.
